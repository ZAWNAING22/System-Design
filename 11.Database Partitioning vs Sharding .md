### Core Comparison

| Features | Database Partitioning | Database Sharding |
| --- | --- | --- |
| **Server Count** | Single DB Server | Multiple DB Servers |
| **Data Location** | Same DB instance | Different DB instances |
| **Network Communication** | Minimal (Local bus/in-memory) | High (Distributed network) |
| **Scalability** | Limited (Vertical / Single node bounds) | Massive (Horizontal scaling) |
| **Complexity** | Lower | Higher (Routing, distributed transactions) |

---

### When to Use Which?

**Choose Database Partitioning when:**

* The database still fits comfortably on a single machine's disk, CPU, and memory.
* The primary goal is reducing query latency by scanning only relevant sub-tables (e.g., querying orders from only the current year).
* You want easier data lifecycle management (e.g., dropping or archiving an entire year's worth of data in a single partition drop).
* You want low operational overhead without managing cluster routing or multi-node sync.

**Choose Database Sharding when:**

* Data volume, write throughput, or IOPS exceed the hardware limits of a single enterprise server (Vertical scaling ceiling reached).
* The application requires high availability and fault isolation—failure of one shard doesn't take down the entire dataset.
* You need geographic data residency (e.g., EU users on EU database nodes, US users on US nodes).
* Cost optimization demands using multiple cheap, commodity instances instead of one massive, expensive server.
